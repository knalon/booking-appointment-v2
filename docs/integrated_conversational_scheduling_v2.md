# Integrated conversational scheduling v2 — milestone 1.2.2

Prerequisites: conversational NLP classification/routing v4, scheduling v1, faculty accounts/workspace v1, and the earlier matching test correction. Demo availability seed v1 is optional but recommended. Apply this patch by merging backend/, frontend/, docs/ into your project root. No schema migrations, new dependencies or data reset. Back up source and database first.

## Behaviour
- All new consultations are exactly 30 minutes. NLP no longer asks about duration; the backend overwrites attempted duration overrides. Existing final JSON is immutable. New confirmed records use schema 1.3; old academic/technical routing remains compatible with the previous rules.
- During intake, the model translates multilingual natural language into canonical date/time values; Django validates them before confirmation. Unsupported or ambiguous values remain missing, requiring clarification. The local learner date is included in the provider context. Relative dates are resolved before confirmation. For legacy records the original confirmation date anchors relative preferences; dates that have passed never silently move to another day. If a legacy preference cannot be interpreted or the learner's time zone changed, start a new request.
- Supported date values: ISO date, today, tomorrow, day after tomorrow, weekday/this weekday (nearest occurrence including today), flexible, ASAP. Supported times: exact HH:MM or AM/PM, after/before a time, explicit same-day range, morning (09–12), afternoon (12–17), evening (17–21), flexible/ASAP. No overnight ranges. 30 local calendar days including today. Flexible means the learner is genuinely available for any offered time; learners should state their own commitments during intake. Only a single preferred date and time range is currently represented; multiple disjoint constraints need a new request or coordinator help. No institutional learner calendar integration yet.
- React automatically requests scheduling on opening the confirmed consultation; no duplicate window form or initial search button. Django derives windows from the immutable request, not browser parameters, and evaluates all eligible faculty before displaying up to three. Academic recommendation snapshot is created if absent. Existing scheduling runs are reused on revisit; Refresh availability explicitly recalculates (and clears any provisional selection after confirmation in the UI).
- If no suitable preferred slots exist, a second search can return clearly labelled alternative slots within the next 30 days, only where existing academic and final thresholds are met. Alternative selection explicitly accepts the changed time; no appointment is booked or held. Alternatives receive 0.75 availability score, preferred slots 1.0; compatible mode receives 1.0. Original weights, exact-topic preference and minimum academic threshold retained. For explicit ASAP, earliest slot takes priority within the existing eligible exact-topic-first pool. Named preferences retain priority for ordinary searches. No booking or calendar synchronization introduced.
- Slots start every 15 minutes, except an exact requested start may be off-grid. Every new slot lasts 30 minutes. Busy, inactive or outside-working-hours windows excluded. The backend rechecks the latest run and current availability when selecting. Historical runs of another duration remain visible, but cannot be selected until refreshed. Existing windows and prior confirmed requests are not deleted or rewritten.
- Staff review keeps the academic and scheduling score breakdowns. Learners see a single final recommendation panel with rounded slot buttons; first six slots per faculty shown initially, expandable. No availability is fabricated.
